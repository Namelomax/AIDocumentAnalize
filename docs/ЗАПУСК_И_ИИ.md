# Запуск стенда и подключение ИИ-моделей

Эта инструкция — для тех, кто впервые разворачивает «Инспектор ИИ» и хочет
подключить к нему языковую модель и модель OCR. Короткий обзор проекта и
список остальной документации — в [`docs/README.md`](README.md).

## 1. Требования

- Docker и Docker Compose (плагин `docker compose`, не отдельный `docker-compose`).
- Для распознавания сканов и гипотез свободного поиска нужна отдельно
  запущенная ИИ-модель за OpenAI-совместимым интерфейсом (LM Studio, vLLM и
  т. п.) — сам стенд её не поднимает и не содержит. Если эта модель работает
  на GPU (например, vLLM на H100), на машине с моделью должен быть установлен
  **NVIDIA Container Toolkit**. Самому докер-компоуз стенду (`api`, `worker`,
  `web`, инфраструктура) GPU не нужен — в `docker-compose.yml` для него нет
  ни одного `--gpus`/`nvidia`-требования.
- Свободные порты на хосте:

  | Порт | Сервис | Назначение |
  |---|---|---|
  | 8080 | web | веб-интерфейс |
  | 3000 | api | REST API |
  | 9090 | prometheus | UI Prometheus |
  | 3001 | grafana | UI Grafana |
  | 8090 | rin-mock | локальная заглушка ИАИС «РиН» |
  | 3310 | clamav | антивирусное сканирование (clamd) |
  | 5432 | postgres | БД |
  | 5672, 15672 | rabbitmq | AMQP и management UI |
  | 9000, 9001 | minio | S3 API и консоль |

  Redis (6379) в `docker-compose.yml` наружу не опубликован — он доступен
  только внутри докер-сети, отдельного порта на хосте не занимает.

## 2. Запуск

### С интернетом

```bash
docker compose up -d --build
```

`api`, `worker` и `web` соберутся из исходников, остальные образы (Postgres,
Redis, RabbitMQ, MinIO, ClamAV, Prometheus, Grafana) будут скачаны по
зафиксированным digest'ам.

### Офлайн (проверочный стенд без интернета)

Заранее, на машине с интернетом, собирается архив образов:

```bash
bash scripts/build-offline-bundle.sh
```

Он положит `dist/inspector-images.tar`. На самом стенде:

```bash
docker load -i dist/inspector-images.tar
docker compose up -d
```

Так как у `api`, `worker`, `web` и `rin-mock` в `docker-compose.yml` указано
поле `image:`, `docker compose up` без `--build` возьмёт уже загруженные
образы и сеть не понадобится.

### Проверка, что всё поднялось

```bash
docker compose ps
```

Все сервисы должны быть `healthy`. `clamav` стартует дольше остальных —
загружает антивирусные базы, это может занять от ~10 до ~60 секунд
(`start_period: 30s` в healthcheck), `api` ждёт его готовности перед своим
собственным healthcheck, так что просто подождите ещё немного, если `api`
пока `starting`.

Интерфейс — `http://localhost:8080`. Демонстрационные учётки (создаются
автоматически при пустой таблице пользователей):

| Логин | Роль | Пароль |
|---|---|---|
| `admin` | Администратор | `admin123` |
| `inspector` | Инспектор | `inspector123` |
| `supervisor` | Супервизор | `supervisor123` |
| `ml` | ML-инженер | `ml123` |

## 3. Подключение ИИ-моделей

**Система полностью работает и без моделей.** Без них честно возвращаются
частичные результаты: гипотезы свободного поиска — «модель недоступна»,
страницы без текстового слоя — статус `LOW_QUALITY` вместо распознавания.
Ничего не падает и не блокирует остальной пайплайн.

Нужны два независимых OpenAI-совместимых эндпоинта (может быть один и тот же
сервер на оба):

- **Языковая модель** — для гипотез свободного поиска (раздел 9.5 ТЗ).
  Переменные: `LLM_BASE_URL`, `LLM_MODEL`, `LLM_TIMEOUT_S` (по умолчанию 60
  секунд), `LLM_BATCH_SIZE` (по умолчанию 5 — столько пар помещений уходит в
  одном запросе к модели).
- **Модель OCR** — для страниц без текстового слоя (п.1 стр. 16 ТЗ, «не менее
  300 dpi»). Переменные: `OCR_MODEL`, `OCR_BASE_URL` (если не задать, берёт
  значение `LLM_BASE_URL` — удобно, когда обе модели раздаёт один сервер),
  `OCR_TIMEOUT_S` (по умолчанию 120 секунд — распознавание одной полосы
  страницы у контрольной модели занимало 40–90 с), `OCR_DPI` (по умолчанию
  300).

Задаются через `.env` рядом с `docker-compose.yml`:

```bash
cp .env.example .env
# отредактировать LLM_*/OCR_* в .env
docker compose up -d worker
```

Важно: `docker compose up -d worker` после правки `.env` пересоздаёт
контейнер `worker` (подхватывает новые переменные окружения) — пересборка
образа (`--build`) для этого не нужна, `docker compose restart worker`
не подойдёт, потому что просто перезапускает старый контейнер со старыми
переменными.

### Вариант А — LM Studio (для разработки)

1. Загрузить в LM Studio модели `qwen/qwen3.8-27b` (языковая) и `glm-ocr`
   (OCR).
2. Включить в LM Studio «Serve on Local Network» и запустить сервер на порту
   1234 — иначе из докер-контейнера (это не хост) сервер недоступен.
3. В `.env`:

   ```
   LLM_BASE_URL=http://host.docker.internal:1234/v1
   LLM_MODEL=qwen/qwen3.8-27b
   OCR_MODEL=glm-ocr
   ```

   (`OCR_BASE_URL` можно не задавать — по умолчанию совпадёт с `LLM_BASE_URL`,
   LM Studio раздаёт обе модели с одного порта.)

### Вариант Б — vLLM на стенде с GPU (H100)

Пример запуска vLLM со своим OpenAI-совместимым сервером:

```bash
docker run --gpus all -p 8000:8000 \
  vllm/vllm-openai --model <путь-или-HF-id> --served-model-name qwen3-27b
```

На офлайн-стенде веса модели нужно заранее скачать и смонтировать как volume
(`-v /path/to/weights:/path/in/container`) — на самом стенде интернета нет.
Имя модели в `LLM_MODEL` обязано совпадать с тем, что передано в
`--served-model-name`.

В `.env`:

```
LLM_BASE_URL=http://host.docker.internal:8000/v1
LLM_MODEL=qwen3-27b
```

(либо адрес сервиса, если vLLM добавлен в `docker-compose.yml` как ещё один
сервис в общей сети — тогда вместо `host.docker.internal` используется имя
этого сервиса).

### Проверка связи

С хоста:

```bash
curl http://localhost:1234/v1/models
```

Изнутри контейнера `worker` (важно проверять именно оттуда — у контейнера
своя сетевая видимость, отличная от хоста):

```bash
docker compose exec worker python -c "import urllib.request;print(urllib.request.urlopen('http://host.docker.internal:1234/v1/models').read()[:200])"
```

### Где увидеть, что модель действительно используется

- Логи воркера: `docker compose logs -f worker` — сообщения о вызовах модели
  для гипотез и OCR.
- Экран «Гипотезы» в интерфейсе — вместо «модель недоступна» появляются
  реальные предположения (SUSPICION).
- Grafana (`http://localhost:3001`, дашборд «Инспектор ИИ — эксплуатация») —
  панели по задержке и ошибкам обращений к LLM
  (`inspector_llm_request_duration_seconds`, `inspector_llm_requests_total`).

## 4. Быстрая проверка сценария

Вручную: создать объект → загрузить пару ПД+РД → запустить обработку →
дождаться статуса READY → открыть протокол → проверить кандидатов (рамки
evidence на изображениях страниц) → финализировать → выгрузить PDF/DOCX/XML.

Автоматически (тот же сценарий скриптом):

```bash
bash tests/e2e/test_upload_flow.sh
```

Нужны Python 3 и виртуальное окружение воркера (`services/worker/.venv`) —
скрипт использует эталонные листы из `.e2e-tmp/Задание/`. Эта папка не входит
в репозиторий: чтобы сценарий отработал, туда нужно предварительно положить
материалы заказчика (эталонный комплект ПД/РД).

## 5. Частые проблемы

- **Поменял код, а в контейнере ничего не изменилось.** У `api`, `worker` и
  `web` в `docker-compose.yml` указано поле `image:` — обычный
  `docker compose up` без `--build` берёт уже собранный образ. Пересобирайте
  явно: `docker compose up -d --build`.
- **Порт занят.** Проверьте, что на хосте свободны порты из таблицы в
  разделе 1 (особенно часто конфликтуют 5432, 3000, 8080).
- **Модель недоступна из контейнера, хотя на хосте работает.** В LM Studio
  должно быть включено «Serve on Local Network»; в `.env` — именно
  `host.docker.internal`, а не `localhost`/`127.0.0.1` (из контейнера это не
  хост); проверьте, что фаервол не блокирует входящие подключения к порту
  модели.
- **ClamAV долго стартует.** Это нормально — на первый запуск он
  разворачивает антивирусные базы, `api` дожидается его healthcheck перед
  собственным. Подождите до минуты, дальше `docker compose ps` покажет
  `healthy`.
- **Ежедневная проверка целостности хранилища (раздел 31 ТЗ) падает с
  FAILURES на старой БД разработчика.** Обычно это «мусорные» строки от
  старых версий тестов, не настоящий инцидент — см.
  `scripts/dev/cleanup-orphan-test-files.sh` (по умолчанию только показывает,
  что нашёл; `--apply` — удаляет).

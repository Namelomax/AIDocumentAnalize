## 1. О продукте одним абзацем

Государственный инспектор строительного надзора сегодня вручную сверяет три массива документации по объекту капитального строительства: **проектную (ПД)** — то, что утвердила экспертиза; **рабочую (РД)** — то, по чему реально строят; и **исполнительную (ИД)** — то, что фактически построили и задокументировали. Расхождения между ними — это и есть нарушения. Сверка идёт по **132 контролируемым параметрам** (площади, этажность, класс бетона, ширина эвакуационных выходов, конфигурация вентиляции и т. д.) и занимает недели.

«Инспектор ИИ» загружает комплекты документов, извлекает значения этих параметров из PDF-чертежей и текстов, сопоставляет три стадии между собой и формирует **предварительный протокол** с кандидатами в нарушения. Дальше инспектор проходит по кандидатам и принимает решение по каждому.

---

## 2. Главная смысловая идея, без которой интерфейс будет неправильным

> **ИИ не находит нарушения. ИИ находит кандидатов. Нарушением что-либо становится только после решения инспектора.**

Это не юридическая формальность, а требование исходного ТЗ, и оно определяет весь визуальный язык продукта. Практические следствия для дизайна:

1. **Нигде в интерфейсе ИИ не должен выглядеть так, будто он вынес вердикт.** Никаких «Обнаружено 14 нарушений» на дашборде. Правильно: «14 кандидатов на проверку».
2. **Приоритет проверки (HIGH / MEDIUM / LOW) — это очередь, а не тяжесть нарушения.** Его нельзя красить в красный. HIGH означает «посмотри это первым», а не «тут точно плохо». Из 132 параметров HIGH имеют 106 — если покрасить их красным, экран будет полностью красным и потеряет смысл.
3. **Инспектор — не оператор, а эксперт, принимающий решение под свою подпись.** Интерфейс обязан давать ему всё для решения на одном экране и не заставлять никуда переходить за доказательствами.
4. **Отсутствие документа — не нарушение.** Статусы про качество входных данных (нет файла, нельзя сопоставить, непонятно какая редакция актуальна) визуально отделены от содержательных расхождений и живут в отдельных таблицах протокола.

Если по макету человек, впервые его увидевший, решит, что система сама выносит нарушения, — макет надо переделать.

## 3. Пользователь и сценарий, который мы показываем

**Роль в демо — одна: государственный инспектор строительного надзора.** Роли администратора (управление нормативной базой) и ML-инженера (отчёты по дообучению) в объём макетов **не входят** — их не рисуем.

**Портрет:** 35–55 лет, работает за десктопом с большим монитором, по образованию строитель, а не айтишник. Ведёт одновременно 10–40 объектов. Работает с интерфейсом ежедневно по несколько часов, поэтому плотность информации для него важнее «воздуха», а скорость — важнее анимаций. Читает чертежи лучше, чем таблицы.

**Сквозной сценарий демо (его и проектируем):**

```
Вход → Дашборд объектов → Карточка объекта и загрузка ПД/РД/ИД
     → Обработка (прогресс) → Протокол проверки
     → Верификация кандидатов (главный экран, цикл)
     → Финализация и выгрузка
```

**Две количественные цели из ТЗ, которые проверяются по макету:**

| Метрика | Целевое значение |
|---|---|
| Полный цикл верификации протокола (132 параметра, 14 кандидатов) | **≤ 30 минут** |
| Количество кликов на решение по одному кандидату | **≤ 3** |

Вторая метрика — жёсткое ограничение компоновки. Она означает: **решение по кандидату принимается без единого модального окна и без перехода на другую страницу.** Открыть карточку — 1 клик, выбрать причину — 1 клик, подтвердить — 1 клик. Всё.

## 4. Визуальный язык

### 4.1. Тональность

Государственный сервис для профессионала, а не потребительский продукт. Ориентиры по ощущению: панель управления инфраструктурой, профессиональный CAD-инструмент, банковский бэк-офис. Ориентиры **не** подходящие: лендинг стартапа, мобильное приложение, «умный ассистент» с чат-пузырями.

Конкретно:
- Сдержанно, плотно, без декора. Иллюстраций нет, кроме пустых состояний.
- Никаких градиентов, стекла, теней глубже 2 уровней, скруглений больше 8 px.
- Анимации только функциональные: появление панели, скелетон загрузки, переход между кандидатами. Длительность 120–200 мс.
- Тёмная тема **не требуется**. Делаем только светлую.

### 4.2. Цветовые токены

Все цвета объявляются переменными Figma (Variables) в коллекции `color`. Хардкод цветов в слоях запрещён — иначе экспорт в React даст неподдерживаемый код.

**Нейтральные и фон**

|---|---|---|
| `bg/app` | `#F5F7FA` | Фон приложения |
| `bg/surface` | `#FFFFFF` | Карточки, таблицы, панели |
| `bg/subtle` | `#EDF1F7` | Заголовки таблиц, чередование строк |
| `border/default` | `#E2E8F0` | Границы, разделители |
| `border/strong` | `#CBD5E1` | Границы полей ввода |
| `text/primary` | `#0F172A` | Основной текст, значения |
| `text/secondary` | `#475569` | Подписи, метаданные |
| `text/tertiary` | `#94A3B8` | Плейсхолдеры, отключённое |

**Бренд**

| Токен | HEX | Назначение |
|---|---|---|
| `brand/600` | `#1B4E9B` | Основные кнопки, активные вкладки, ссылки |
| `brand/700` | `#16407F` | Hover |
| `brand/50` | `#E8F0FB` | Выделение активной строки, фон бейджей |

**Статусы находок — главная часть палитры.** Их восемь, и большинство должно быть нейтральным. Цветом выделяются только три содержательных исхода; остальные пять — это состояния данных, они серые с иконкой.

| Статус | Русское название в UI | Текст | Фон | Правило |
|---|---|---|---|---|
| `CONFIRMED_VIOLATION` | Нарушение подтверждено | `#B42318` | `#FEF3F2` | Единственный красный в системе. Только после решения инспектора |
| `CANDIDATE` | Кандидат | `#B54708` | `#FFFAEB` | Янтарный. «Требует решения», не «плохо» |
| `NEGATIVE_VERIFIED` | Проверено, расхождения нет | `#027A48` | `#ECFDF3` | Зелёный |
| `CLARIFICATION_REQUIRED` | Требует уточнения | `#5925DC` | `#F4F3FF` | Фиолетовый — единственное исключение среди «данных», т. к. требует действия |
| `MISSING_EVIDENCE` | Нет доказательства | `#475569` | `#F1F5F9` | Нейтральный + пунктирная рамка. **Не красный** |
| `NOT_APPLICABLE` | Неприменимо | `#64748B` | `#F8FAFC` | Приглушённый, 70 % непрозрачности текста |
| `NOT_COMPARABLE` | Нельзя сопоставить | `#475569` | `#F1F5F9` | Нейтральный + иконка предупреждения |
| `SUSPICION` | Гипотеза | `#026AA2` | `#F0F9FF` | Голубой. Визуально отличается от всех кандидатов Матрицы |

**Приоритет экспертной проверки (HIGH / MEDIUM / LOW)** — отдельный компонент, **не использующий цвет статуса**. Только графит `#475569` и индикатор из трёх засечек: HIGH `▮▮▮`, MEDIUM `▮▮▯`, LOW `▮▯▯`. Подпись рядом текстом.

**Подсветка доказательств на чертежах** — отдельная семантика, не смешивать со статусами:

| Токен | HEX | Назначение |
|---|---|---|
| `evidence/expected` | `#2E90FA` | Область-источник **ожидаемого** значения (как правило ПД) |
| `evidence/actual` | `#F04438` | Область-источник **фактического** значения (РД или ИД) |
| `evidence/context` | `#94A3B8` | Прочие распознанные области, неактивные |

Рамка 2 px, заливка 8 % непрозрачности, скругление 2 px. Это соответствует эталонному комплекту разметки от заказчика, где отклонения отмечены красным.

### 4.3. Типографика

Шрифт: **Inter** (запасной вариант — **Golos Text**, если нужна более «государственная» подача). Один шрифт на весь проект.

| Токен | Размер / межстрочный | Начертание | Применение |
|---|---|---|---|
| `text/display` | 28 / 36 | 600 | Заголовок страницы |
| `text/h1` | 20 / 28 | 600 | Заголовки секций |
| `text/h2` | 16 / 24 | 600 | Заголовки карточек |
| `text/body` | 14 / 20 | 400 | Основной текст, таблицы |
| `text/body-strong` | 14 / 20 | 500 | Значения, важные поля |
| `text/caption` | 12 / 16 | 400 | Метаданные, подписи |
| `text/mono` | 13 / 20 | 400, моно | Шифры документов, SHA-256, коды параметров |

**Обязательно:** для всех числовых значений включить **табличные цифры** (`font-variant-numeric: tabular-nums`). Инспектор сравнивает числа в столбик — они должны быть одной ширины. Это касается колонок «Ожидается» и «Фактически».

Моноширинный шрифт (**JetBrains Mono** или **IBM Plex Mono**) применяется только к машинным идентификаторам: `M-047`, `АНО/150321/1-РД-ОВ1`, `Ред. 2`, хеши.

### 4.4. Сетка и отступы

- Основной макет: **1440 × 900**, минимально поддерживаемая ширина **1280**. Мобильная и планшетная версии **не требуются** — инспектор работает за десктопом, а на телефоне сверять чертежи невозможно.
- Сетка 12 колонок, поля 32 px, межколонник 24 px.
- Шкала отступов кратна 4: `4 / 8 / 12 / 16 / 24 / 32 / 48`.
- Скругления: `4` (бейджи, поля), `8` (карточки, кнопки), `12` (модальные окна). Больше — нельзя.
- Тени: `shadow/sm` = `0 1px 2px rgba(15,23,42,.06)`, `shadow/md` = `0 4px 12px rgba(15,23,42,.08)`. Третьего уровня нет.

### 4.5. Плотность

Профессиональный инструмент: высота строки таблицы **40 px**, высота кнопки **36 px** (крупная — 40), высота поля ввода **36 px**. Компактнее обычных веб-продуктов, и это намеренно — на экране должно помещаться 14–18 строк протокола без прокрутки.

Компоненты собираются как Figma Components с вариантами (Variants) и Auto Layout. Именование — в единственном числе, латиницей, через слэш: `Badge/Status`, `Table/Row`, `Panel/Evidence`.

### Компоненты, которые надо спроектировать особенно тщательно

**`Badge/Status`.** Восемь вариантов, но выглядеть они должны как одна семья. Формат: точка-индикатор 6 px + текст 12/16 + фон. Отличаться должны цветом и наличием иконки, а не формой.

**`Panel/Evidence`** — сердце продукта. Панель просмотра одного листа документа. Содержит:
- шапку: `Badge/Stage`, шифр документа моноширинным, `Ред. N`, `Badge/Approval`, номер листа/страницы;
- область просмотра со скроллом и зумом (кнопки `−` / `100 %` / `+` / «вписать»);
- оверлей подсветки области-доказательства прямоугольником или полигоном;
- подпись под оверлеем с извлечённым значением;
- нижнюю строку с `SHA-256` (усечённый, с кнопкой копирования) и ссылкой «Открыть исходный файл».

**`Chip/ReasonCode`.** При отклонении кандидата код причины обязателен. Набор фиксированный, формулировки — ровно такие:
`Актуальная редакция выбрана неверно` · `Есть согласованное изменение` · `Ошибка OCR` · `Ошибка привязки` · `Параметр неприменим` · `Иное (укажите)`.
Выбор — одним кликом по чипу, не выпадающим списком. Это экономит клик из бюджета в три.

## 6. Правила, нарушение которых считается ошибкой макета

1. Красный цвет применяется **только** к статусу `CONFIRMED_VIOLATION` и к подсветке `evidence/actual`. Больше нигде.
2. Приоритет HIGH/MEDIUM/LOW **не окрашивается** в цвета статусов.
3. Слово «нарушение» без уточнения применяется **только** к подтверждённым инспектором находкам. Для остальных — «кандидат», «гипотеза», «расхождение».
4. Решение по кандидату (подтвердить / отклонить / уточнить) принимается **без модального окна**.
5. Статусы комплектности (`MISSING_EVIDENCE`, `NOT_APPLICABLE`, `NOT_COMPARABLE`, `CLARIFICATION_REQUIRED`) показываются **в отдельных таблицах**, а не вперемешку с кандидатами.
6. У каждого кандидата на экране одновременно видны: ожидаемое значение, фактическое значение, оба источника с указанием стадии/шифра/редакции и подсвеченные области на листах. Ничего из этого не прячется за «показать подробнее».
7. Все восемь статусов находок и все шесть статусов процесса присутствуют в макетах хотя бы один раз — иначе нечего будет верстать.
8. Данные в макетах — правдоподобные строительные, не `Lorem ipsum` и не `John Doe`. См. раздел 7.9.

## 7. Экраны

Всего восемь экранов. Для каждого указано: назначение, состав, состояния, критерии приёмки.

### 7.1. Э1. Вход

**Назначение:** минимальный экран, нужен для полноты демо.

**Состав:** логотип и название «Инспектор ИИ», подзаголовок «Сервис сверки проектной, рабочей и исполнительной документации», поля «Логин» и «Пароль», кнопка «Войти», ссылка «Вход по электронной подписи» (неактивная, как задел).

**Состояния:** обычное, ошибка авторизации, загрузка.

**Приёмка:** экран занимает не больше одного кадра, без промо-текста и иллюстраций.

---

### 7.2. Э2. Дашборд объектов

**Назначение:** инспектор видит все свои объекты и понимает, за какой браться.

**Состав:**
- Шапка: хлебные крошки, поиск по объектам, кнопка `+ Новая проверка`.
- Строка сводки — четыре плитки: «Объектов в работе», «Протоколов ожидают верификации», «Кандидатов к рассмотрению», «Финализировано за месяц». Цифры крупные, табличные.
- Панель фильтров: раздел ПД (выпадающий список из 16 разделов Матрицы), статус процесса, диапазон дат, приоритет.
- Таблица или сетка карточек объектов. По умолчанию — **таблица**, режим карточек как переключатель.

**Колонки таблицы:** цветовой индикатор · Объект (название + адрес) · Застройщик · Комплектность (три мини-бейджа ПД/РД/ИД) · Статус процесса · Кандидатов · Подтверждено · Обновлён · действия.

**Цветовая индикация объекта — трёхуровневая, задана в ТЗ:**
- зелёный — протокол финализирован, подтверждённых нарушений нет;
- жёлтый — есть кандидаты, ожидающие решения, либо неполная комплектность;
- красный — есть подтверждённые инспектором нарушения.

Индикатор — вертикальная полоса 4 px слева у строки, не заливка всей строки.

**Состояния:** список, пустое состояние («Ещё нет ни одного объекта» + кнопка), пустой результат фильтра, загрузка (скелетон на 6 строк).

**Приёмка:** нигде на экране нет формулировки, приписывающей нарушения системе. Колонка называется «Кандидатов», а не «Нарушений».

### 7.3. Э3. Объект и загрузка комплекта

**Назначение:** загрузить документы по трём стадиям и увидеть комплектность до запуска проверки.

**Состав:**
- Шапка объекта: название, адрес, застройщик, подрядчик, номер разрешения на строительство. Всё компактно, в две строки.
- Вкладки: `Документы` · `Протоколы` · `История`. Активна первая.
- **Три колонки-зоны загрузки: ПД / РД / ИД.** Каждая колонка — самостоятельный `Dropzone` со списком уже загруженных файлов под ним.
- Каждый файл в списке: иконка формата, имя, размер, `Badge/Stage`, марка комплекта (АР, КР, ОВ, ВК…), шифр моноширинным, редакция, `Badge/Approval`, число листов, усечённый SHA-256, кнопка удаления.
- Отдельный блок **«Реестр файлов»**: загрузка сопроводительного CSV/XLSX/JSON. Рядом пояснение: без реестра пакет принимается со статусом «Требует уточнения». Показать оба состояния — реестр загружен и не загружен.
- Панель комплектности справа или снизу: по каждой стадии один из статусов — `Загружено полностью` / `Загружено частично` / `Отсутствует`. Например: «ПД — загружено полностью (12 файлов)», «РД — загружено частично (5 из 15)», «ИД — отсутствует».
- Плашка **«Тип проверки»**, которая пересчитывается от состава: `FULL` (есть все три) · `ПД + РД` · `ПД + ИД` · `РД + ИД` · `Одна стадия` · `Частичная загрузка`. Подписывать по-русски, машинный код — мелким моноширинным рядом.
- Кнопка `Запустить проверку` — основная, внизу справа. Неактивна, пока не загружена хотя бы одна стадия.

**Ограничения, которые надо отразить в интерфейсе:** форматы PDF, DOCX, XML; максимум **50 МБ** на файл; максимум **200 МБ** на пакет. Показать индикатор занятого объёма пакета.

**Состояния ошибок — обязательны все пять, в виде тостов или строк-ошибок у файла:**

| Ситуация | Сообщение в интерфейсе |
|---|---|
| Неподдерживаемый формат | «Формат не поддерживается. Допустимы PDF, DOCX, XML» |
| Повреждённый PDF | «Файл повреждён и не может быть прочитан. Загрузите заново» |
| Файл больше 50 МБ | «Файл превышает 50 МБ» |
| Пакет больше 200 МБ | «Превышен общий лимит пакета — 200 МБ» |
| Таймаут обработки | «Превышено время обработки. Выполняется повторная попытка (2 из 2)» |

**Приёмка:** видно, что дозагрузка возможна позже — рядом с кнопкой запуска есть пояснение «Файлы можно дозагрузить до финализации протокола».

### 7.4. Э4. Обработка

**Назначение:** показать, что система работает, и чем именно она занята. Экран асинхронный, инспектор может уйти.

**Состав:**
- Крупный индикатор этапов (`Progress/Steps`), четыре шага: **Распознавание (OCR)** → **Извлечение значений (NLP)** → **Анализ чертежей (CV)** → **Сопоставление 132 параметров**. Текущий шаг подсвечен, пройденные — с галочкой.
- Под каждым шагом — счётчик: «Обработано 68 из 143 листов», «Извлечено значений: 411», «Сопоставлено параметров: 87 из 132».
- Лента событий справа: список строк вида `14:02:11 · Файл АНО/150321/1-РД-ОВ1 · распознано 18 листов`. Моноширинное время, обычный текст.
- Плашка: «Можно закрыть страницу — проверка продолжится. Мы уведомим о готовности протокола».
- Оценка оставшегося времени.

**Состояния:** в работе, ошибка на одном файле (остальные продолжают обрабатываться — показать частичную ошибку, а не падение всего), завершено с переходом на протокол.

**Приёмка:** этап `PARSING` явно запрещает дозагрузку — соответствующая кнопка отключена с пояснением в подсказке.

### 7.5. Э5. Протокол проверки

**Назначение:** полная картина результата. Отсюда инспектор уходит в верификацию.

**Состав:**
- Шапка протокола: номер, объект, дата формирования, версия протокола, статус процесса (`Готов к верификации`). Мелким моноширинным — версии, обеспечивающие воспроизводимость: `matrix_version`, `model_version`, `dataset_version`, хеш входного пакета. Это требование ТЗ, его надо показать, пусть и неброско.
- Блок **«Статус загрузки документов»** — три строки с бейджами комплектности.
- Блок **«Тип проверки»** — плашка сценария.
- Полоса сводки: «132 параметра проверено · 14 кандидатов · 3 подтверждено · 96 расхождений не выявлено · 12 без доказательств · 7 неприменимо».
- **Пять вкладок — ровно те, что требует ТЗ:**

| Вкладка | Содержание |
|---|---|
| `Комплектность и сопоставимость` | Параметры со статусами `MISSING_EVIDENCE`, `NOT_APPLICABLE`, `NOT_COMPARABLE`, `CLARIFICATION_REQUIRED` |
| `Кандидаты` | `CANDIDATE`, **вкладка по умолчанию** |
| `Подтверждённые нарушения` | `CONFIRMED_VIOLATION` |
| `Проверено, расхождений нет` | `NEGATIVE_VERIFIED` |
| `Гипотезы свободного поиска` | `SUSPICION` |

  В ярлыке каждой вкладки — счётчик.

- Таблица внутри вкладки. Колонки: код параметра (`M-047`, моно) · Раздел · Наименование параметра · Ожидается · Фактически · Δ · Источники (три мини-бейджа ПД/РД/ИД, неактивные серые, если источника нет) · Приоритет · Статус · кнопка `Проверить`.
- Фильтры над таблицей: раздел Матрицы, приоритет, статус, «только с доказательствами».
- Кнопки справа вверху: `Экспорт` (выпадающий: PDF, DOCX, XML), `Завершить верификацию` (неактивна, пока есть необработанные кандидаты — обязательно показать это состояние с подсказкой-пояснением).

**Особенность вкладки «Гипотезы»:** у каждой строки вместо `Δ` — уровень уверенности модели (`0.87`) и способ обнаружения: `Логический анализ` / `Семантический диссонанс` / `Нормативный анализ` / `ML-паттерн`. Действие на строке — `Привязать доказательства`, а не «Подтвердить»: гипотеза не может стать нарушением напрямую.

**Состояния:** заполненный протокол; вкладка без записей; версия протокола обновлена после дозагрузки (плашка «Протокол обновлён, версия 2. Изменения по 6 параметрам» со ссылкой на предыдущую версию).

**Приёмка:** пять вкладок присутствуют и названы по смыслу; кандидаты и комплектность не смешаны в одной таблице.

### 7.6. Э6. Верификация кандидата — главный экран

**Левая панель — очередь.** Список всех кандидатов протокола, отсортированный по приоритету. Каждая строка: код параметра моноширинным, короткое название, `Badge/Priority`, отметка о принятом решении. Текущий кандидат выделен. Показать счётчик «3 из 14» и прогресс-полосу. Фильтр по приоритету и статусу. Панель сворачивается.

**Центральная панель — доказательство.** Сверху шапка кандидата: код, наименование параметра, раздел, приоритет, единица измерения.

Затем **блок сравнения значений** — два крупных поля рядом: «Ожидается» (значение + подпись стадии-источника) и «Фактически». Значения набраны крупно (24 px, табличные цифры). Под ними — дельта и текстовое описание сработавшего триггера («Расхождение > 0», «Понижение класса», «< 0,9 м»).

Ниже — **сплит-вью просмотра документов**: два экземпляра `Panel/Evidence` рядом, слева источник ожидаемого (обычно ПД), справа источник фактического (РД или ИД). Если параметр требует всех трёх стадий — переключатель на третью панель или вкладки `ПД | РД | ИД` внутри правой панели. Синхронный зум — переключаемый.

На каждой панели: подсвеченная область-доказательство, шифр документа, редакция, статус утверждения, номер листа и страницы, усечённый SHA-256.

Внизу центральной панели — **блок обоснования**: текст объяснения от модели, ссылка на нормативную базу (`СП 1.13130.2020, п. 4.2.1`), поле «Согласованное изменение» со значением либо «не найдено». Последнее критично: если согласованное изменение существует, оно отменяет исходное требование, и это прямое основание для отклонения кандидата.

**Правая панель — решение.** Три кнопки действий, расположенные вертикально и крупно:
- `Подтвердить нарушение` — основная, единственная в системе с красной семантикой;
- `Отклонить` — вторичная;
- `Требует уточнения` — вторичная.

Под ними — набор `Chip/ReasonCode`. Он появляется **сразу после выбора «Отклонить»**, без модального окна, в той же панели. Поле комментария. Кнопка подтверждения решения.

Внизу панели — блок «Разделить на атомарные находки» для составных кандидатов: по ТЗ составной кандидат нельзя подтвердить частично, инспектор обязан разбить его на отдельные находки, каждая со своим решением. Показать это состояние хотя бы на одном макете.

**Бюджет кликов — покажите его соблюдение:**
- Подтверждение: `Подтвердить нарушение` → `Сохранить` = **2 клика**, переход к следующему кандидату автоматический.
- Отклонение: `Отклонить` → чип причины → `Сохранить` = **3 клика**.

**Клавиатурные сокращения** — обязательны, вынести в подсказку внизу экрана: `1` подтвердить, `2` отклонить, `3` уточнить, `→` следующий, `←` предыдущий, `Space` увеличить чертёж.

**Состояния экрана (все нужны в макете):**
1. Кандидат не рассмотрен, решение не принято.
2. Выбрано «Отклонить», раскрыты коды причин.
3. Решение принято, панель в подтверждённом виде, кнопка «Изменить решение».
4. У кандидата отсутствует источник по одной стадии — панель со статусом `MISSING_EVIDENCE` и кнопкой `Дозагрузить документ`.
5. Конфликт редакций — `CLARIFICATION_REQUIRED`: вместо сравнения показан выбор между двумя редакциями с их метаданными и полем обоснования выбора.
6. Составной кандидат с предложением разбить на атомарные находки.
7. Очередь пройдена: «Все кандидаты обработаны» + кнопка `Перейти к финализации`.

**Приёмка:** решение принимается без модальных окон; ожидаемое, фактическое и оба чертежа видны одновременно без прокрутки на 1440×900.

### 7.7. Э7. Финализация и выгрузка

**Назначение:** зафиксировать протокол и передать его во внешнюю систему.

**Состав:**
- Сводка перед финализацией: обработано кандидатов, подтверждено нарушений, отклонено, перенесено в «требует уточнения», отдельным перечнем — записи `MISSING_EVIDENCE` с пояснением «не включаются в число нарушений».
- Блокирующая проверка: если остались необработанные кандидаты, кнопка финализации неактивна, показан список того, что мешает.
- Модальное окно подтверждения (это единственное допустимое место для модалки, кроме отмены финализации): «После финализации дозагрузка документов и изменение решений станут невозможны». Подтверждение осознанным действием.
- Состояние после финализации: протокол помечен как финализированный, все действия заблокированы, экран визуально «запечатан».
- Блок выгрузки: `PDF` · `DOCX` · `XML`.
- Блок передачи в **ИАИС «Разрешения и нарушения»**: статус синхронизации `Не отправлено` / `Отправка` / `Отправлено` / `Ожидает повтора`. Для последнего — пояснение «Внешняя система недоступна. Повторная отправка через 5 минут (попытка 2 из 3). Финализированное решение при этом сохраняется». Подчеркнуть, что сбой передачи не отменяет решение инспектора.
- Кнопка `Отменить финализацию` — доступна только администратору или супервизору, с обязательным указанием причины и предупреждением о записи в журнал аудита. Показать отдельным состоянием.

**Приёмка:** видно, что во внешнюю систему уходят только подтверждённые инспектором записи.

### 7.8. Э8. Гипотезы свободного поиска

Можно реализовать как отдельный экран либо как развёрнутый вид пятой вкладки протокола — на усмотрение дизайнера, но карточка гипотезы должна отличаться от карточки кандидата.

**Состав карточки гипотезы:** способ обнаружения, уровень уверенности модели в виде шкалы, описание («В РД отсутствует лифтовая шахта при 15 этажах»), ссылки на листы ПД и РД, нормативное основание, приоритет.

**Ключевое отличие:** у гипотезы **нет** кнопки «Подтвердить нарушение». Единственное действие — `Привязать доказательства`, после чего гипотеза становится кандидатом и уходит в обычную очередь верификации. Второе действие — `Отклонить гипотезу`. Рядом постоянная плашка: «Гипотезы не входят в число нарушений и не используются для обучения модели».

## 8. Требования к файлу Figma

1. **Переменные.** Все цвета, отступы, скругления и типографические стили — в Figma Variables и Text Styles. Прямые значения в слоях не допускаются: Figma Make превращает переменные в токены, а хардкод — в магические числа.
2. **Auto Layout везде.** Каждый фрейм, каждая карточка, каждая строка таблицы. Абсолютное позиционирование допустимо только для оверлеев подсветки на чертежах.
3. **Компоненты и варианты.** Повторяющиеся элементы — только компонентами. Варианты вместо копий. Свойства компонентов (Component Properties) для текста и иконок.
4. **Именование слоёв.** Осмысленные латинские имена: `EvidencePanel`, `StatusBadge`, `CandidateQueue`, `DecisionPanel`. Не `Frame 427`, не `Group 12`, не кириллица в именах слоёв — она ломает генерацию имён компонентов React.
5. **Структура файла — страницы:**
   `00 · Cover` · `01 · Tokens` · `02 · Components` · `03 · Screens` · `04 · States` · `05 · Flow`
6. **Страница `05 · Flow`** — схема переходов между экранами со стрелками. Нужна и для защиты проекта, и для генерации роутинга.
7. **Прототип** — кликабельный по сквозному сценарию из раздела 3. Достаточно основного пути, без ветвлений.
8. **Иконки** — один набор на весь проект. Рекомендуется **Lucide** (совместим с React-экспортом). Свои иконки не рисовать.

## 9. Требования к React-проекту из Figma Make

Код после генерации забирает команда разработки и подключает к реальному API. Чтобы это было возможно, соблюдайте следующее.

**Стек:** React 18 + TypeScript + Vite, Tailwind CSS. Без Next.js, без серверных компонентов, без библиотек состояния.

**Структура:**
```
src/
  components/   — переиспользуемые элементы (Button, StatusBadge, EvidencePanel…)
  screens/      — по одному файлу на экран
  mocks/        — все демо-данные, только здесь
  types/        — типы данных
  styles/       — токены в CSS-переменных
```

**Обязательные правила:**

1. **Никаких данных внутри компонентов.** Все тексты объектов, кандидатов, значений — в `src/mocks/*.ts` в виде типизированных массивов. Компонент получает данные через props. Это главное требование: мы будем менять источник данных на API, и если данные вшиты в JSX, придётся переписывать всё.
2. **Статусы — строковые литеральные типы,** ровно в том написании, что в ТЗ:
   ```ts
   type FindingStatus =
     | 'CANDIDATE' | 'CONFIRMED_VIOLATION' | 'NEGATIVE_VERIFIED'
     | 'MISSING_EVIDENCE' | 'NOT_APPLICABLE' | 'NOT_COMPARABLE'
     | 'CLARIFICATION_REQUIRED' | 'SUSPICION';

   type ProcessStatus =
     | 'PENDING' | 'PARSING' | 'READY' | 'VERIFYING' | 'COMPLETED' | 'FINALIZED';

   type DocStage = 'PD' | 'RD' | 'ID';
   type ApprovalStatus =
     | 'DRAFT' | 'APPROVED' | 'FOR_CONSTRUCTION' | 'SUPERSEDED' | 'CANCELLED';
   type ReviewPriority = 'HIGH' | 'MEDIUM' | 'LOW';
   ```
   Русские подписи берутся из словаря `statusLabels`, а не хардкодятся в разметке.
3. **Координаты подсветки доказательств** — нормализованные в диапазоне `[0;1]` относительно страницы, в формате `[x1, y1, x2, y2]`. Так их отдаёт бэкенд, и так их надо принимать в компоненте:
   ```ts
   interface EvidenceFragment {
     fileId: string;
     sha256: string;
     stage: DocStage;
     documentCode: string;
     revision: string;
     approvalStatus: ApprovalStatus;
     sheetPage: number;
     bbox: [number, number, number, number]; // нормализованные [0;1]
     extractedValue: string;
     role: 'expected' | 'actual';
   }
   ```
   Оверлей позиционируется в процентах от размера подложки, **не в пикселях** — иначе подсветка разъедется при другом масштабе чертежа.
4. **Токены** — CSS-переменные в `:root`, значения совпадают с Figma Variables один в один.
5. **Никаких вызовов сети.** Ни `fetch`, ни `axios`, ни внешних картинок по URL. Изображения — локальные файлы в `public/`.
6. **Доступность по минимуму:** осмысленные `aria-label` на кнопках-иконках, видимый фокус на всех интерактивных элементах, контраст текста не ниже 4.5:1. Контраст надо проверить для янтарного `#B54708` и голубого `#026AA2` на их фонах.

**Отдача:**
- ссылка на Figma-файл с доступом на просмотр и комментирование;
- ZIP-архив либо репозиторий с React-проектом;
- `README.md` с командами запуска;
- короткая записка: что отрисовано, что осталось заглушкой, какие места требуют доработки.

## 12. Открытые вопросы к заказчику

# Архитектура системы «Инспектор ИИ»

Сервис автоматической сверки проектной, рабочей и исполнительной документации объектов капитального строительства.

**Версия:** 1.0
**Дата:** 24 сентября 2026
**Статус:** принята к реализации

---

## 1. Условия, в которых мы строим

### 1.1. Проверочный стенд

Организаторы зафиксировали конфигурацию, на которой будет запускаться решение:

| Ресурс | Выделяется команде |
|---|---|
| GPU | 1 × NVIDIA H100, 80 ГБ VRAM |
| CPU | 24 физических ядра / 48 потоков |
| RAM | до 640 ГБ |
| Диск | не менее 300 ГБ |
| ОС | Linux + Docker + NVIDIA Container Toolkit |

### 1.2. Ограничения, которые определяют архитектуру

1. **Внешние API запрещены полностью**, включая подключение к собственному публичному API команды. Все модели — локальные, с открытыми весами, внутри поставляемого образа.
2. **Проверка идёт после дедлайна, без нашего участия**, образы могут запускаться повторно. Следствие: система обязана подниматься одной командой, работать полностью офлайн и не требовать ручных шагов.
3. **Драйвер NVIDIA в образ не включаем**, CUDA runtime и все зависимости — включаем.
4. **Нормативы производительности меряются на GPU.** CPU-режим допустим как резерв, но по нему не оценивают.
5. **Скрытый тестовый набор.** Метрики считаются на объектах, которых мы не видели. Никакой подгонки под девять эталонных объектов быть не может — ни в промптах, ни в правилах.

### 1.3. Ресурсы команды

3–5 человек, одна–две недели. Это главный ограничитель объёма, и раздел 12 исходит именно из него.

## 2. Ключевые архитектурные решения

Пять решений, из которых следует всё остальное. Каждое — с обоснованием, потому что все они принимались против какой-то более очевидной альтернативы.

### Решение 1. Трёхуровневый конвейер извлечения, где VLM — последняя очередь, а не первая

**Проблема.** ТЗ требует обработать 500 страниц не более чем за 10 минут, то есть **1,2 секунды на страницу**. VLM класса 30B на одной H100 даёт порядка 2–6 секунд на страницу при полном разборе. Прогнать зрительную модель по всем страницам невозможно в норматив — расхождение на порядок.

**Решение.** Разделяем обработку на три уровня по стоимости:

```
Уровень 1  ~20–50 мс/стр   Текстовый слой PDF (PyMuPDF)
           Проектная документация — векторные выгрузки из CAD.
           Текст в них уже есть, вместе с точными координатами.
           Character Accuracy на текстовом слое = 1.0 при пороге 0.95.
                │
                ├─ текста достаточно → на уровень 4
                └─ страница-скан → уровень 2

Уровень 2  ~200–400 мс/стр  OCR на GPU, батчами.
           Только для страниц без текстового слоя.
           Отдаёт ту же структуру, что и уровень 1: текст + bbox.

Уровень 3  ~2–6 с/стр       VLM. Вызывается ТОЛЬКО по страницам,
           которые ретривер отобрал под конкретный параметр.
           Не 500 страниц, а 3–10 на параметр.

Уровень 4  —                Индексация и сопоставление. CPU, без моделей.
```

**Проверка гипотезы проведена.** Из файла `Комплект_предметной_разметки.pdf` обычным парсером без OCR извлекаются экспликации помещений с площадями, размерные цепочки, содержимое штампов и спецификации. То есть уровень 1 покрывает основную массу проектной документации.

**Следствие для нормативов:** 500 страниц проходят уровни 1–2 примерно за 2 минуты при норме 10. Запас уходит на уровень 3, который работает по выборке.

### Решение 2. Параметры описываются декларативно, а не кодом

**Проблема.** 132 параметра — это 132 функции извлечения и сравнения. За две недели их не написать и тем более не отладить.

**Решение.** Каждый параметр — YAML-спецификация, которую исполняет один общий движок. Матрица из `Матрица_параметров_редакция1.1.xlsx` конвертируется в 132 заготовки скриптом, дальше команда доводит их по одной.

**Критично:** незаполненная спецификация не молчит и не падает, а честно возвращает `NOT_COMPARABLE` с указанием причины. Система с первого дня формально работает по всем 132 параметрам — по части из них сообщая, что сопоставить не может. Это ровно то поведение, которого требует ТЗ, и оно же защищает нас на скрытом тесте: непокрытый параметр даёт не ложное срабатывание, а честный отказ, который не портит Precision.

### Решение 3. Модель закрыта интерфейсом, а не именем

Конкретные веса подбираются экспериментом в первый день. В коде нет упоминаний модели — только `VisionProvider` и `EmbeddingProvider` с реализацией поверх OpenAI-совместимого эндпоинта vLLM, поднятого локально.

Это не абстракция ради абстракции: она нужна, чтобы в первый день прогнать две-три модели на девяти эталонных объектах и выбрать по цифрам, не переписывая конвейер.

### Решение 4. Бэкенд по ТЗ: Node.js + Python, но с тонким Node

ТЗ прямо называет Node.js серверной частью и Python — ML-модулями, и жюри это сверит. Сохраняем, но распределяем так, чтобы стык был минимальным:

- **Node.js** — аутентификация, CRUD объектов и файлов, протоколы, верификация, аудит, экспорт, SSE для прогресса. Никакой обработки документов.
- **Python** — весь конвейер от приёма файла до формирования findings.
- **Граница** — только очередь RabbitMQ и общая база Postgres. Никаких синхронных вызовов между ними.

**Грабли, которые обходим заранее:** Celery использует собственный формат сообщений, публиковать его из Node болезненно. Поэтому Node публикует **обычный JSON** в очередь, а Python-воркер читает его через `aio-pika` и сам маршрутизирует по внутренним обработчикам. Celery не используем.

### Решение 5. Нарушение назначает только инспектор

Архитектурное, а не только интерфейсное решение. Движок сравнения физически не умеет выставлять `CONFIRMED_VIOLATION` — этот статус пишется только эндпоинтом вердикта, и только с непустым `user_id`. В БД стоит ограничение:

```sql
CONSTRAINT confirmed_requires_inspector CHECK (
  finding_status <> 'CONFIRMED_VIOLATION' OR verified_by IS NOT NULL
)
```

Это дешёвая страховка от того, что кто-нибудь в спешке поставит статус из воркера.

### Распределение VRAM на одной H100 80 ГБ

| Компонент | Объём | Примечание |
|---|---|---|
| VLM ~30B в **FP8** | ~30 ГБ | H100 поддерживает FP8 нативно, потери качества минимальны |
| KV-кеш VLM | ~15 ГБ | обеспечивает батчинг, без него нормативы не берутся |
| OCR-модель | 1–3 ГБ | PaddleOCR PP-OCRv5 либо Surya |
| Эмбеддер | 1–2 ГБ | FRIDA либо multilingual-e5-large |
| Резерв | ~30 ГБ | пики, реранкер, запас на вторую модель при экспериментах |

Тот же VLM в bf16 занял бы ~60 ГБ весов и ~72 ГБ вместе с кешем — влезает, но не оставляет места под батчинг, а без батчинга нормативы недостижимы. **Квантование в FP8 здесь не оптимизация, а условие работоспособности.**

## 4. Конвейер обработки

### Этап A. Приём и реестр (CPU, без моделей)

1. Антивирусная проверка (ClamAV с вшитыми в образ сигнатурами).
2. Валидация формата (PDF / DOCX / XML), размера файла (≤ 50 МБ) и пакета (≤ 200 МБ).
3. Вычисление SHA-256, укладка в MinIO по контент-хешу. Перезапись файла под тем же `file_id` **запрещена** — повторная загрузка создаёт новую запись.
4. Разбор машиночитаемого реестра (CSV / XLSX / JSON). **Без реестра пакет принимается со статусом `CLARIFICATION_REQUIRED`** — это требование из `Перечень_исполнительной_документации`.
5. Построение цепочек редакций по `predecessor_id` / `successor_id`.
6. Расчёт комплектности по стадиям и определение сценария загрузки: `FULL`, `PD_RD_ONLY`, `PD_ID_ONLY`, `RD_ID_ONLY`, `SINGLE_ONLY`, `PARTIALLY_LOADED`.

### Этап B. Рендер и текстовый слой (CPU, параллельно по ядрам)

Через PyMuPDF для каждой страницы:
- извлечение текстовых фрагментов с координатами;
- рендер в PNG 200 dpi (кропы под VLM — 300 dpi по требованию);
- **нормализация координат в `[0;1]` с учётом `CropBox`, `MediaBox` и `Rotate`.**

Последнее — отдельный пункт ТЗ и главный источник тихих ошибок. Повёрнутый лист без учёта `Rotate` даёт подсветку, смещённую на 90°, причём всё выглядит работающим. Нормализацию покрываем модульными тестами на всех четырёх углах поворота **до** того, как она попадёт в конвейер.

Решение о необходимости OCR: если на странице меньше порогового числа символов — считаем сканом.

### Этап C. OCR (GPU, батчами) — только для страниц-сканов

На выходе та же структура, что у этапа B: текст плюс нормализованный bbox. Зоны низкого качества и рукописный текст помечаются `LOW_QUALITY` либо `ABSTAIN` — ТЗ прямо требует, чтобы система умела отказываться, а не выдумывать. Покрытие и доля таких зон пишутся в протокол.

### Этап D. Метаданные документа

Из штампа (нижний правый угол листа для CAD-чертежей) извлекаются: шифр документа, редакция, стадия, марка комплекта, номер листа, признаки утверждения («В производство работ», «Выполнено согласно проекту»).

**Реестр имеет приоритет над штампом.** Расхождение между ними не отбрасывается молча, а фиксируется и уводит документ в `CLARIFICATION_REQUIRED`.

### Этап E. Индексация

- чанки текста по страницам и смысловым регионам → эмбеддинги → pgvector;
- полнотекстовый индекс Postgres с русским словарём;
- гибридный поиск: ключевые слова плюс семантика, с реранкингом.

### Этап F. Извлечение параметров

Для каждой спецификации параметра:

1. **Отбор страниц-кандидатов** — по якорям из спецификации (ключевые слова, регулярные выражения) и по семантическому поиску. Обычно 3–10 страниц на параметр из сотен.
2. **Извлечение по модальности:**

| Модальность | Как | Доля из 132 |
|---|---|---|
| `scalar_text` | регулярные выражения по текстовому слою, VLM — только как запасной путь | ~55 |
| `doc_presence` | проверка по реестру файлов, модели не нужны | ~11 |
| `drawing_entity` | кроп региона → VLM с грounding → наличие и количество сущностей | ~38 |
| `drawing_measure` | калибровка по размерной линейке → измерение → сверка с порогом | ~28 |

3. **Результат извлечения** всегда включает: значение, единицу, `file_id`, SHA-256, стадию, шифр, редакцию, статус утверждения, лист/страницу, нормализованный bbox и уверенность.

### Этап G. Сборка доказательных групп

Единица результата — `evidence_group`: объект + атомарный параметр + актуальные сопоставимые редакции ПД/РД/ИД + доказательные фрагменты.

Правила выбора источника (из `Перечень_исполнительной_документации`, реализуются буквально):

| Ситуация | Результат |
|---|---|
| Одна применимая утверждённая редакция | использовать её, зафиксировать `file_id` и SHA-256 |
| Новая редакция явно заменяет старую | старую сохранить для аудита, из сравнения исключить |
| Несколько редакций без однозначного статуса | `CLARIFICATION_REQUIRED`, вывод о нарушении заблокирован |
| Обязательный документ отсутствует | `MISSING_EVIDENCE`, в число нарушений не входит |
| Документ неприменим к объекту | `NOT_APPLICABLE` с обязательным основанием |
| Файл нечитаем, листы не сопоставлены | `NOT_COMPARABLE` |

**Устаревшая редакция не может использоваться как эталон ни при каких условиях.**

### Этап H. Сравнение

Движок правил, не модель. Из блока `compare` спецификации: сравнение значений, расчёт дельты, проверка порога. Результат — `CANDIDATE` либо `NEGATIVE_VERIFIED`.

`NEGATIVE_VERIFIED` формируется **обязательно**, а не только при расхождении: проверенные отрицательные группы нужны для оценки ложных срабатываний, по ним считается отдельный порог FPR ≤ 0,10.

### Этап I. Формирование протокола

Версионированный документ с пятью раздельными таблицами (комплектность / кандидаты / подтверждённые / отрицательные / гипотезы) и обязательной фиксацией `matrix_version`, `model_version`, `dataset_version`, `input_manifest_hash`.

**Инкрементальное обновление при дозагрузке:** пересчитываются только параметры, которых коснулись новые файлы. Определяется по индексу «параметр → задействованные `file_id`». Предыдущая версия протокола сохраняется.

## 5. Спецификация параметра

Формат, который исполняет движок. Матрица конвертируется в такие файлы скриптом `tools/matrix2specs.py`.

```yaml
- code: M-047
  section: АР
  name: Ширина эвакуационных дверей
  unit: м
  data_type: number
  modality: drawing_measure
  priority: HIGH

  sources:
    PD:
      discipline: [АР]
      anchors: ["ведомость заполнения проемов", "спецификация дверей"]
      required: true
    RD:
      discipline: [АР]
      anchors: ["спецификация дверей", "ведомость проемов"]
      required: true
    ID:
      discipline: [ID]
      anchors: ["акт освидетельствования"]
      required: false

  compare:
    op: lt
    threshold: 0.9
    scope: actual
    tolerance: 0.0

  normative:
    sp: "СП 1.13130.2020, п. 4.2.1"

  status_when_unimplemented: NOT_COMPARABLE
```

Поля `sources.anchors` берутся напрямую из колонок «Источник в ПД / РД / ИД» Матрицы, `compare` — из колонки «Логика ИИ-связи», `priority` — из колонки приоритета. Конвертация даёт рабочую заготовку по каждому из 132 параметров автоматически.

## 6. Модель данных

Шестнадцать таблиц из раздела 10 ТЗ. Ключевые:

```sql
-- Объекты капитального строительства
CREATE TABLE objects (
  id            UUID PRIMARY KEY,
  name          TEXT NOT NULL,
  address       TEXT,
  customer      TEXT,
  contractor    TEXT,
  permit_number TEXT
);

-- Реестр файлов. Перезапись под тем же id запрещена
CREATE TABLE files (
  id              UUID PRIMARY KEY,
  object_id       UUID NOT NULL REFERENCES objects(id),
  doc_stage       doc_stage_enum NOT NULL,         -- PD | RD | ID
  discipline      TEXT,
  document_code   TEXT NOT NULL,
  revision        TEXT NOT NULL,
  approval_status approval_enum NOT NULL,
  approval_date   DATE,
  predecessor_id  UUID REFERENCES files(id),
  successor_id    UUID REFERENCES files(id),
  file_hash       CHAR(64) NOT NULL,
  storage_key     TEXT NOT NULL,
  page_count      INT,
  signature_status TEXT,
  uploaded_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (object_id, document_code, revision, file_hash)
);

-- Доказательные фрагменты с координатами
CREATE TABLE evidence_fragments (
  id                 UUID PRIMARY KEY,
  evidence_group_id  UUID NOT NULL,
  file_id            UUID NOT NULL REFERENCES files(id),
  stage              doc_stage_enum NOT NULL,
  sheet_page         INT NOT NULL,
  bbox_norm          REAL[4] NOT NULL,             -- строго [0;1]
  polygon_norm       REAL[],
  extracted_value    TEXT,
  role               TEXT NOT NULL,                -- expected | actual
  confidence         REAL,
  CONSTRAINT bbox_normalized CHECK (
    bbox_norm[1] BETWEEN 0 AND 1 AND bbox_norm[2] BETWEEN 0 AND 1 AND
    bbox_norm[3] BETWEEN 0 AND 1 AND bbox_norm[4] BETWEEN 0 AND 1
  )
);

-- Результаты сравнения
CREATE TABLE checks (
  id                  UUID PRIMARY KEY,
  protocol_id         UUID NOT NULL REFERENCES protocols(id),
  param_code          TEXT NOT NULL,
  object_id           UUID NOT NULL REFERENCES objects(id),
  evidence_group_id   UUID NOT NULL,
  expected_value      TEXT,
  actual_value        TEXT,
  delta               TEXT,
  completeness_status completeness_enum NOT NULL,
  finding_status      finding_enum NOT NULL,
  review_priority     priority_enum NOT NULL,
  approved_change_ref TEXT,
  reasoning           TEXT,
  verified_by         UUID REFERENCES users(id),
  verified_at         TIMESTAMPTZ,
  reason_code         TEXT,
  inspector_comment   TEXT,
  CONSTRAINT confirmed_requires_inspector CHECK (
    finding_status <> 'CONFIRMED_VIOLATION' OR verified_by IS NOT NULL
  ),
  CONSTRAINT rejected_requires_reason CHECK (
    finding_status <> 'NEGATIVE_VERIFIED' OR verified_by IS NULL OR reason_code IS NOT NULL
  )
);
```

Оба ограничения `CHECK` — это перевод требований ТЗ в гарантии базы. Проверка на уровне приложения здесь недостаточна: писать в `checks` будут и Node, и Python.

Остальные таблицы по ТЗ: `params`, `protocols`, `rejection_log`, `dispute_log`, `suspicions`, `logical_rules`, `normative_base`, `ml_retraining_log`, `audit_log`, `monitoring_metrics`, `dataset_items`, `model_versions`.

## 7. Контракт API

REST over HTTPS, JSON, схема OpenAPI 3.0, асинхронная pull-модель.

| Метод | Путь | Назначение |

Вердикт инспектора:

```json
POST /api/v1/findings/{id}/verdict
{
  "decision": "CONFIRMED_VIOLATION | NEGATIVE_VERIFIED | CLARIFICATION_REQUIRED",
  "reason_code": "OUTDATED_REVISION | APPROVED_CHANGE | OCR_ERROR |
                  LINKING_ERROR | NOT_APPLICABLE | OTHER",
  "comment": "строка"
}
```

`reason_code` обязателен при `NEGATIVE_VERIFIED`. Проверяется и в Zod-схеме, и ограничением базы.

**Передача в ИАИС «РиН»** разрешена только при статусе `PROTOCOL_FINALIZED`. При недоступности внешней системы протокол сохраняет статус, а синхронизация уходит в `PENDING_SYNC` с повторами через 1, 5 и 15 минут. **Сбой внешней передачи не отменяет и не изменяет решение инспектора** — отдельно оговорено в ТЗ. Для хакатона реализуем как заглушку с полным журналированием: реальной ИАИС у нас нет.

## 8. Модуль свободного поиска гипотез

Четыре подхода из ТЗ, с честной оценкой реализуемости за две недели:

| Подход | Как реализуем | Реалистичность |
|---|---|---|
| Логический анализ | база правил `logical_rules` в YAML: «если этажей > 10, должен быть лифт» | высокая |
| Семантический диссонанс | сравнение наименований помещений между стадиями через эмбеддинги: «Техническое» против «Склад ГСМ» | высокая |
| Нормативный анализ | проверка по таблице `normative_base` с порогами | высокая |
| ML-паттерн-анализ | статистические выбросы по историческим данным | **низкая — исторических данных нет** |

По четвёртому подходу закладываем интерфейс и простой детектор выбросов, но в презентации честно говорим, что без накопленной истории он не обучен. Выдумывать здесь хуже, чем признать.

Гипотеза получает статус `SUSPICION`, **не входит в число нарушений и не используется как положительная учебная метка**. Перевод в `CANDIDATE` возможен только после привязки конкретных источников и координат.

## 9. Контур GOLD и дообучение

Единица разметки — `evidence_group`. Положительная метка допустима только для `CONFIRMED_VIOLATION`, отрицательная — только для `NEGATIVE_VERIFIED`. `CANDIDATE`, `SUSPICION`, `MISSING_EVIDENCE` и незавершённые решения в обучение не попадают.

**Разбиение по объектам:** все страницы, документы и редакции одного объекта лежат строго в одном из наборов `train` / `validation` / `hidden_test`. Реализуется группировкой по `object_id` при формировании `dataset_items` — не по файлам и не по страницам.

Публикация модели запрещена автоматически. Требуется: прохождение порогов раздела 14 ТЗ, отсутствие падения Recall по любой обязательной категории более чем на 2 п.п., отсутствие роста FPR более чем на 2 п.п. Решение подписывается, откат сохраняется.

За две недели это реализуется как контур сбора и версионирования, без реального цикла дообучения. Так и говорим.

## 10. Соответствие нормативам производительности

| Норматив ТЗ | Требование | Как обеспечиваем |
|---|---|---|
| Загрузка 10 файлов по 50 МБ | ≤ 2 мин | прямая заливка в MinIO, хеширование потоком |
| OCR PDF до 100 страниц | ≤ 3 мин | уровни 1–2, параллельно по 24 ядрам |
| OCR PDF до 500 страниц | ≤ 10 мин | то же; текстовый слой снимает основную нагрузку |
| Сравнение 132 параметров | ≤ 2 мин | движок правил на CPU, VLM уже отработал на этапе F |
| Генерация протокола | ≤ 30 с | сборка из БД, PDF через WeasyPrint |
| ML-анализ одного параметра (NLP) | ≤ 500 мс | эмбеддинги предпосчитаны на этапе E |
| Инкрементальное обновление | ≤ 1 мин | пересчёт только затронутых параметров |
| Отклик API, 95-й процентиль | ≤ 200 мс | Node не делает тяжёлой работы, всё в очереди |
| 100 одновременных инспекторов | — | Node масштабируется репликами, GPU не на критическом пути чтения |

**Главный риск норматива** — этап F на чертёжных параметрах. Если ретривер отберёт слишком много страниц, VLM не уложится. Поэтому на количество страниц, уходящих на уровень 3, стоит жёсткий лимит из конфигурации, с деградацией в `NOT_COMPARABLE` при превышении. Лучше честный отказ, чем срыв норматива.

## 11. Развёртывание

```
docker compose up   →   web · api · worker · vllm · postgres · redis · rabbitmq · minio
```

Требования к образам:
- CUDA runtime внутри, драйвер NVIDIA — нет;
- все веса моделей вшиты в образ, скачивание при старте отсутствует;
- миграции базы и загрузка 132 спецификаций — автоматически при первом старте;
- демонстрационные данные (девять эталонных объектов) — опциональным сидом по переменной окружения;
- healthcheck у каждого сервиса, `depends_on: condition: service_healthy`;
- ожидаемый размер образа с весами — 40–60 ГБ, при 300 ГБ доступного диска это приемлемо.

**Вопрос закрыт:** несколько образов допускаются, обязательное условие — запуск одной командой, по одному сервису на роль (одна база, один брокер и так далее). Остаёмся на `docker compose`, сборка всего в один контейнер под `supervisord` не требуется.

## 13. Риски

| Риск | Вероятность | Что делаем |
|---|---|---|
| Проектные PDF окажутся сканами, а не векторными | средняя | уровень 2 уже в архитектуре; пострадает скорость, но не работоспособность |
